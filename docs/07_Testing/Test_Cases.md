**Assurance caveat on the "73 passing tests" figure.** A larger suite is not automatically a better one, and one of these tests runs directly over a live defect without noticing: `interactionChecker.spec.ts`'s "always includes a source citation and disclaimer" (TC-027) calls `checkInteractions(["a","b"])`, which — **measured by execution on 2026-08-21** — returns `flagged: true` with **five** spurious severe-interaction matches, and asserts nothing about any of them. What the growth from 32 to 73 did buy is narrower and more specific: five findings that were previously *argued* are now *pinned by a test that fails against the pre-fix code* — payer binding (TC-110), cross-language box-key parity (TC-120…TC-125), the transposed ARC-28 event field order (TC-150), the under-reported grant box MBR (TC-153), and the address-checksum / error-disclosure pair (TC-172, TC-173).

## A.2 Cross-language box-key parity — `contracts/tests/test_box_keys.py` + `api/test/boxKeyParity.spec.ts`

The consent box key is derived independently in three languages with three different crypto APIs — AVM `op.sha256` in `contracts/smart_contracts/consent/contract.py`, `node:crypto` `createHash` in `api/src/services/algorand.ts`, and WebCrypto `crypto.subtle.digest` in `web/lib/consent.ts`. Nothing checked that they agreed, and a one-byte divergence does not raise: `check_access` reads an empty box and returns `false`, so the failure presents as "the patient's grant mysteriously doesn't work". **G-08 / NFR-011 is closed by a single shared fixture, `api/test/fixtures/box-key-vectors.json`, asserted by both suites** — one file, two languages, so drift fails a build rather than a demo.

## A.6 Payer-identity binding — `api/test/x402Payer.spec.ts`

The most consequential group in the register, because it is the one that turns the consent check from a paywall into an authorisation decision.

The x402 middleware proves that *a* payment settled; it does not tell the handler *whose*. `requesterAddress` arrives in the request body, and `grant_access` transactions publish valid `(patient, requester, scope)` triples to any indexer — so until the two were bound, a stranger could pay the ordinary $0.05, name someone else's authorised requester, and be handed the record, with the forged identity written into the patient's immutable audit trail. **The fix inverts that: the payment signature *is* the authentication.** `api/src/x402Payer.ts` decodes the verified `PAYMENT-SIGNATURE` header, reads the AVM `exact` payload (`{paymentGroup, paymentIndex}`), and recovers the address that actually signed the payment transaction; `api/src/routes/records.ts` returns **403** unless it equals `requesterAddress`. No new credential, no new key, no session — the caller already proved possession of that key in order to pay at all.

These tests build a **real** signed USDC transfer with `algosdk` and wrap it in a genuine x402 v2 AVM payload, so they exercise the decode path rather than a stub of it. Measured: **6 tests**.

## C.4 Concurrency and audit sequencing

Target file: **new** `api/test/algorand.concurrency.spec.ts`.

**Read this before writing the assertions — the obvious test would pass for the wrong reason.**

The **contract already self-assigns the sequence number**. `log_access` reads its own `audit_seq` box, computes `next_seq` itself, writes both boxes, and returns the value it assigned (`contracts/smart_contracts/consent/contract.py:224-236`). The client-side `predictedSeq` in `api/src/services/algorand.ts:158-159` exists **only to populate the AVM box-reference array** (`:169-172`), because Algorand requires every box a transaction touches to be declared in advance; the sequence actually reported to the caller is the contract's return value, with `predictedSeq` used merely as a fallback (`:176`).

Consequently the race failure mode is a **rejected transaction, not a corrupted or misordered log**. Two concurrent calls both read count `n` and both declare box `a‖patient‖itob(n+1)`. The first executes and the contract writes sequence `n+1`. The second executes, the contract computes `n+2`, and the write fails because box `a‖patient‖itob(n+2)` was never declared in that transaction's reference array.

**Therefore: a test asserting "sequence numbers are unique and correctly ordered" would pass whether or not the lock exists, because the contract guarantees that property on its own. It would prove nothing.** The assertion with teeth is that no call is *rejected*.

`api/fly.toml` now sets `max_machines_running = 1`, and says why in a comment: the lock is in-process, so a second machine would reintroduce exactly the collision it prevents. That converts the defect formerly filed as D-7 from *unbounded* to *bounded and declared* — the topology can no longer drift into the broken configuration by accident. It does not make the system horizontally scalable, which is **G-11**, still open: the ceiling is a constraint, not a fix, and lifting it needs the sequence prediction moved off the client or the lock moved into shared state.
